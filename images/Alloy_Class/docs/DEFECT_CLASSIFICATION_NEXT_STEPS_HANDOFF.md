### Current prototype flow

1. defect images are prepared in `inputs`
2. optional defect metadata is built from production coordinates + image manifest
3. metadata is attached to image-name keyed records in `config/defect_size_metadata.csv`
4. structured classification optionally injects retained metadata into the prompt as supporting context
5. outputs are written as JSON and JSONL for comparison and later joining

### Current metadata builder behavior

- reads production coordinates from `outputs/defects/DEFECT_COORDINATES_EXTENDED.csv`

- skips incomplete image-manifest rows with missing join keys
- writes Alloy-side metadata keyed by `image_name`

## Image-Manifest Validation Findings

### Coverage result

Using the current production files:

- source coordinates: `../../outputs/defects/DEFECT_COORDINATES_EXTENDED.csv`
- source image manifest: `../../outputs/defects/DEFECT_COORDINATES_EXTENDED_IMAGES.csv`

The validated recent coverage result was:

- recent coordinate rows with `IMAGE_COUNT > 0`: `1232`
- matched in image manifest: `1231`
- missing in image manifest: `1`
- coverage: `99.92%`

This is acceptable for current Phase 1 experimentation.

### Why the image manifest looks sparse

Many manifest rows are inventory-only rows added from files already on disk.

Those rows may have:

- `LOCAL_IMAGE_FILE`
- derived `DEFECT_ID`
- derived `IMAGE_ID`
- derived `INSPECTION_TIME`

but still lack enriched context such as:

- `CLASS`
- `LAYER`
- `LOT` / `LOT7`
- `SIZE_X` / `SIZE_Y` / `SIZE_D` / `AREA`

That sparsity does not mean the recent query-side enrichment failed broadly. It mainly reflects historical inventory rows that were not rebuilt from live coordinate joins.

### Inventory-only handling

The image-reconciliation utility now marks such rows explicitly using `INVENTORY_ONLY`.

The Alloy metadata builder now skips incomplete manifest rows instead of counting them as metadata-join failures.

Most recent validation result for Alloy metadata build:

- `rows_written=2296`
- `unmatched_image_rows=0`
- `skipped_incomplete_image_rows=143`

Interpretation:

- there are no remaining true coordinate-to-manifest mismatches in the Alloy metadata join for rows with complete keys
- the skipped rows are incomplete manifest inventory rows, not current join failures

### Single known recent manifest gap

One recent coordinate defect with images was not present in the manifest by exact defect key:

- `WAFER_KEY=8052019`
- `DEFECT_ID=89`
- `INSPECTION_TIME=2026-05-27 15:55:11`
- `IMAGE_COUNT=4`
- `CLASS=SMALL_PARTICLE`
- `LAYER=8M6CL`

Other defects from the same wafer inspection were present in the manifest, so this appears to be a per-defect manifest gap rather than a whole-wafer fetch failure.

Because current image retrieval is tuned around the typical `IMAGE_ID` pair `[2, 3]`, this should be kept in mind for later handling of multi-image defects.

## Tiered Classification Direction

### Recommended near-term structure

Use a staged rather than monolithic classification flow.

Proposed tiers:

1. Pair-aware descriptive understanding
   - consume brightfield and darkfield together when available
   - summarize visible morphology, contrast behavior, and uncertainty
2. Structured defect categorization
   - map image evidence plus metadata context into stable output fields
   - keep `review_required` explicit
3. Escalation / analyst triage
   - flag ambiguous, low-confidence, or metadata-image conflicts
4. Optional evaluator pass
   - compare caption-style and structured outputs for consistency

### Why tiering is preferable here

- image quality and defect separability are variable
- metadata can help disambiguate some cases but should not dominate the visual evidence
- BF/DF pairs provide complementary information
- some defect classes likely need an uncertainty-first workflow instead of forced single-label assignment

## Recommended Phase 2 Design

### Inputs

- brightfield image
- darkfield image
- retained defect metadata:
  - `SIZE_X`
  - `SIZE_Y`
  - `SIZE_D`
  - `AREA`
  - `MANUAL_OPTICAL_CLASS`
- pipeline context when useful:
  - `CLASS`
  - `FINEBIN`
  - `STATUS`
  - `PILOT_STATUS`
  - chamber / layer context

### Outputs

Recommended pair-level output contract:

- `run_id`
- `pair_key`
- `brightfield_image_name`
- `darkfield_image_name`
- `model_name`
- `prompt_version`
- `primary_class`
- `secondary_class`
- `confidence`
- `review_required`
- `morphology_summary`
- `bf_df_consistency`
- `metadata_alignment`
- `rationale`

### Decision policy

- if visual evidence is weak, prefer `review_required=true`
- if metadata suggests one class but imagery suggests another, record the conflict explicitly
- do not convert source metadata into pseudo-ground-truth labels unless their semantics are confirmed

## Immediate Next Steps For The Next Agent

1. Refactor from single-image classification emphasis toward pair-aware BF/DF evaluation.
2. Add a pair-level manifest or pairing helper so BF and DF images are classified together.
3. Add `MANUAL_OPTICAL_CLASS` to report views where useful, but treat it as source metadata rather than truth.
4. Prototype a tiered prompt that first describes, then classifies, then decides whether review is required.
5. Add a pair-level HTML report that shows:
   - BF image
   - DF image
   - caption summary
   - structured output
   - retained metadata
   - review flag
6. Keep the current metadata builder join strict; do not pull inventory-only rows into Alloy metadata unless a later recovery step reconstructs their keys.

## Boundaries

Do not treat this work as production scheduling or ScriptHost hardening yet.

That later phase should happen only after:

- pair-level behavior is acceptable
- prompt/schema stability is acceptable
- uncertainty handling is acceptable
- metadata usage is understood well enough to avoid overfitting
